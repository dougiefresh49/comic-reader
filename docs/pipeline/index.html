Comic Reader Pipeline Map

The ingest workflow turns a set of uploaded page images into a readable issue: sixteen steps in STEP_ORDER, four of them review gates that pause the run for the owner. This page shows what each step reads, decides, calls and writes, with every fact tied to a file:line on commit 861c22b or to a SELECT on the two-page smoke test (smoke-test/issue-smoke). It maps the pipeline; it does not propose changes.

What the pipeline isOne Workflow SDK workflow, ingestPipeline in ingest-pipeline.ts:81, that sequences "use step" functions from src/workflows/steps/. The order is STEP_ORDER, ingest-pipeline.ts:52.
Where it runsVercel Workflow on the deployed site, or a local world under pnpm dev; the world is picked per process by withWorkflow. Both write the same production Supabase project. A run started locally can be resumed only from that local server.
Where state livesSupabase rows and Storage only: issues.pipeline_step and the pause columns, pipeline_runs.steps for timings and gate waits, llm_calls for spend. Steps keep nothing of their own; a resume re-reads the DB.
What costs moneyRoboflow (page analysis), Gemini HIGH and MEDIUM (face ID, OCR, speaker, sort, voice descriptions), ElevenLabs (Voice Design, which also takes one of 30 shared voice slots, and TTS). The #97 smoke run spent about $0.86 of Gemini on 2 pages before pausing.

How it moves

Start, pause, resume, cancel, fail

The orchestrator is ingest-pipeline.ts:81-390. It only sequences steps; every DB write lives in a "use step" function, and the body must not read the clock because it replays (shared.ts:161-166).

How an ingest starts

  • One control POSTs /api/admin/trigger-ingest to start a run: PipelineActions, which the dashboard and the pipeline hub both render, behind HTTP basic auth (middleware.ts:13-15). A start with no fromStep, or from the first step, on an issue that already has bubbles answers 409 reason: "has-bubbles" and writes nothing until the admin types the issue id into the confirm (#319).
  • The route (trigger-ingest/route.ts:10) reads the issue, checks that no run of this issue is live (any of the 4 gate hooks found, or a pipeline_runs row still running whose Workflow run is pending or running) and answers 409 if one is (:95-133, #208 "A paused ingest run blocks the next run of the same issue with HookConflictError under pnpm dev"). Stale state passes (decisions row 129).
  • It writes issues.pipeline_step = fromStep ?? "roboflow-page-analyze" with the pause flags cleared (:141-157), calls start(ingestPipeline, [{bookId, issueId, fromStep}]) (:159-165) and inserts pipeline_runs {status:'running', steps:{runId, fromStep, skipped:[]}} (:167-176). An insert failure still returns 200 with a warning; that run then has no row and every timing write logs "no running pipeline_runs row".
  • Inside the run, getPageList runs first whatever fromStep is: pages ordered by number, then a Storage listing; a page row with no page-NN.webp is a FatalError (shared.ts:40-103). Zero pages: FatalError("No pages found for this issue") (ingest-pipeline.ts:89-92).
  • Each non-gate step does updatePipelineStep(step) (writes pipeline_step, clears the pause flags), recordStepStart, the work, recordStepEnd.

Where it runs

  • withWorkflow in next.config.mjs:6 picks the backend at config load: no VERCEL_DEPLOYMENT_ID means WORKFLOW_TARGET_WORLD=local with run state in that checkout's .next/workflow-data; on Vercel it is Vercel Workflow. The generated runtime routes live under src/app/.well-known/workflow/v1/, gitignored.
  • The two worlds are separate: a run started under local pnpm dev can be resumed or cancelled only from that local server, and the trigger's liveness check sees only its own world. Both write production Supabase. Whether a local and a Vercel run can collide in practice was never tested unconfirmed.
  • scripts/smoke-ingest.ts spawns its own pnpm dev -p 3082 with a temp WORKFLOW_LOCAL_DATA_DIR so each smoke run gets a clean hook store (smoke-ingest.ts:473-484).
  • Steps use a service-role Supabase client from NEXT_PUBLIC_SUPABASE_URL and SUPABASE_SECRET_KEY (step-utils.ts:3-19).
  • Retries: a step that throws an ordinary Error is retried by the runtime; a FatalError fails at once. Lanes 03 and 06 read the default in @workflow/core's dist as DEFAULT_STEP_MAX_RETRIES = 3; lanes 02, 05 and 08 left the count unconfirmed. Two steps set maxRetries = 0: generateVoiceModel (generation.ts:283) and generateAudioBatch (generation.ts:455). lanes disagree Lane 08 wrote that a grep for maxRetries in src/workflows finds none; lanes 03, 04 and 06 cite those two lines. The lines win on this page; see Confidence.

Pause and resume

  • Pause: updatePipelineStep(gate, true) writes pipeline_step=<gate>, pipeline_paused=true, pipeline_paused_at=<gate>, pipeline_paused_url=getPauseUrl(...) (shared.ts:105-127). The base URL is https://$VERCEL_PROJECT_PRODUCTION_URL, else NEXT_PUBLIC_BASE_URL, else http://localhost:3000 (shared.ts:269-286). Slack gets "Pipeline paused" when configured (shared.ts:288-320).
  • Then recordGateWait(open) and await createHook({token}). Hook tokens are ingest:<book>/<issue>/<suffix>; the suffix map is PAUSE_TO_HOOK_STEP in cancel-ingest/hooks.ts:1-6. The public /.well-known/workflow/v1/webhook/[token] route cannot resume these; only server code can.
  • Resume callers all build the same token: the dashboard Resume button through POST /api/admin/resume-hook (resume-hook/route.ts:5-33, writes nothing, 404 "Hook not found or already resumed" on any error), the clusters and bubble-editor approve buttons through the same route, the new-characters page's resumeCharacterReviewAndClearPause (new-characters-resume.ts:37-86) and the casting page's completeCasting (casting/actions.ts:173-231). The last two clear the pause flags themselves, even when no hook was waiting.
  • After a resume the flags clear when the next step's updatePipelineStep runs. The payload {approved: true} is never inspected.
  • fromStep resume: shouldRun(step, fromStep) runs every step at or after fromStep's index; an unknown name runs everything (ingest-pipeline.ts:71-77). It is a new Workflow run with a new runId and a new pipeline_runs row; state comes only from what earlier steps wrote to the DB. A fromStep equal to a gate pauses at that gate again. The dashboard offers it as "Retry: <failed step>", any step in its own STEP_ORDER copy (PipelineActions.tsx:54-71, not imported from the orchestrator), and "Restart from <next step>" when a paused issue's hook is gone (decisions row 55).

Cancel and failure

  • Cancel: dashboard Cancel on a paused row, or "Cancel run <id>" under a refused trigger (#242 "Show the trigger-ingest refusal on the admin page and let cancel-ingest cancel the run it names"), both to cancel-ingest/route.ts:124. It finds the run holding the paused gate's hook (or the newest running row), requires the Workflow run to be pending or running, calls run.cancel(), then compare-and-sets issues.pipeline_step='failed:<pausedAt or step>' with the pause flags cleared and marks the pipeline_runs row cancelled (:239-312). The trigger's 409 text still says cancel-ingest cannot cancel a run it now can (#279 "trigger-ingest's 409 still says cancel-ingest cannot cancel a run it now can").
  • Failure: any throw that escapes lands in the catch at ingest-pipeline.ts:382-390: closePipelineRun("failed"), then markPipelineFailed(currentStep) writes pipeline_step='failed:<step>' and clears the pause flags (shared.ts:252-267). status is not changed. A failure inside getPageList reports failed:roboflow-page-analyze (or failed:<fromStep>). The FatalError branch and the fallthrough do the same thing.
  • Completion: markIssueReady writes pipeline_step='complete', status='ready', pause flags cleared (shared.ts:332-344); closePipelineRun("completed"). Neither touches books.published nor revalidates the reader cache.

What it decides

Cuts the SAM3 character and balloon outlines into each panel's own coordinates so the reader's layered panel view can draw page art, then effects, then the characters and balloons on top again. Nothing a kid hears depends on it, and no later ingest step reads foreground_polygons.

Paid calls

None. Pure geometry over rows step 1 stored.

Logic

  1. Load the segmentation row and the page's panels by sort_order.
  2. mapForegroundPolygons(panels, size, predictions) (vision-rows.ts:318-363): keep classes comic character, person, face, head as characters and speech bubble as bubbles; drop polygons under 3 points; centroid = mean of vertices; the polygon goes to the first panel in sort_order whose box contains the centroid, else dropped. An inset panel loses to whichever comes first in detection order.
  3. Points become panel-local 0..1 fractions, unclamped, so a figure past the panel edge has values outside 0..1 (#219 "Move the foreground-polygon mapping into one helper shared by the workflow and backfill-panels").
  4. Simplify: over 50 vertices runs Ramer-Douglas-Peucker from epsilon 0.005, growing 1.5x while still over 50 and epsilon under 0.1 (vision-rows.ts:298-307).
  5. Consumer: ZenComicReader renders LayeredPanel only in panel view when the active panel has polygons (ZenComicReader.tsx:512-524); it draws the page with an even-odd clip, the effects slot, then the page clipped to the polygons (LayeredPanel.tsx:56-92).
